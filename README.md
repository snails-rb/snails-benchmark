# snails-benchmark

Measures `GET /up` throughput, memory and launch time for a Snails app and a Rails app on the same machine, so the two can be compared without proxy, network or database cost in the way.

Generated defaults on both sides (`snails new`, `rails new --api`), same JSON body, 32 concurrent connections:

| target | RPS | p95 | peak memory | idle memory | launch | image |
|---|---:|---:|---:|---:|---:|---:|
| snails | 57,863 | 1.12 ms | 39 MiB | 14.2 MiB | 8 ms | 138 MiB |
| rails-cluster | 18,547 | 3.99 ms | 866 MiB | 184.4 MiB | 1,556 ms | 416–424 MiB |
| rails-default | 4,920 | 9.44 ms | 141 MiB | 98.4 MiB | 1,531 ms | 416–424 MiB |

Target names are the identifiers `bin/bench` takes, so they stay lowercase. `rails-cluster` is one Puma worker per CPU, the shape Rails needs to use the same cores Snails uses in one process. `rails-default` is `rails new` untouched: one process, five threads. Against the first, Snails answers 3.1× the requests; against the second, 11.8×.

Throughput and peak memory are from the per-request logging-off profile on both sides (`results/2026-11-10-no-logging/`); launch and idle memory come from `results/2026-11-10-boot/`. Medians of three and five runs on one machine, so the ratios travel and the absolute numbers do not.

## What is measured

Three apps, each answering the same `GET /up` with the same JSON body, run in containers on one machine:

- **Snails** — a Snails app created by `snails new`. One process, using every CPU the container is given.
- **Rails** — a `rails new --api` app. It runs in two shapes, because the shape changes the answer:
  - `rails-default`: one process with five threads, which is what `rails new` gives you. Rails' default web server is Puma.
  - `rails-cluster`: one Puma worker process per CPU, which is what Rails needs in order to use the same CPUs Snails uses by default.
- **baseline** — nginx answering `return 200`. It shows the most this machine and load generator can produce, so a generator bottleneck is visible instead of being mistaken for a fast app.

The `-no-logging` variants turn off the per-request log line, and `snails-single-worker` caps the Snails app to one CPU worker. Those exist to isolate a variable, not as separate products.

## Why the measurement is set up this way

Three properties of the two runtimes decide the design.

**Snails runs one process.** A Snails app serves every request from a single process and uses all available CPUs from inside it. Process count is not a setting you can raise, so measuring it would tell you nothing.

**Rails runs one process per worker.** Ruby executes one thread of application code at a time, so a Rails app only uses several CPUs by running several processes, and each process holds its own copy of the application in memory. This is why the comparison needs two Rails shapes and why memory grows with worker count.

**A load generator and a server on the same cores mislead.** If they share cores, the server's share falls as load rises, so a slower server is partly just a server that lost the CPU contest. The generator gets its own cores for that reason.

Two more rules follow from how the numbers behave:

- **Concurrency is what is varied.** Each new connection is a thread the app must run, so a low connection count finishes before the CPUs are used. Levels are swept until throughput stops rising, and the comparison uses the point where it stops.
- **Rounds interleave the targets.** Within a round every target is measured once, so a machine that drifts (heat, background work) drifts for all of them.

## Running it

```sh
bin/bench                                           # 5 targets x 4 concurrency levels x 3 rounds x 20s
bin/bench --vus 8,64 --repeat 1 --duration 8s       # quick check
bin/bench --targets snails-no-logging,rails-cluster-no-logging --vus 32,64
bin/bench --build                                   # rebuild both app images first
bin/boottime                                        # launch time and idle memory
bin/imagesize                                       # image size
```

Requirements:

- Docker
- `mise use -g k6@2.3.0` — the load generator. The version matters because k6's own overhead differs between releases.
- At least 8 CPUs, so the generator and the app can be kept apart. Below that `bin/bench` stops immediately rather than producing a misleading number.
- The `snails` CLI to build the Snails app; `SNAILS_DIR` can point at a checkout instead.

Builds:

```sh
bin/bench --build                                   # both images
apps/snails/bin/build-image --tag bench             # Snails app only
docker build -t rails-api:bench apps/rails-api      # Rails app only
```

The `apps/snails/snails-core/` directory is generated by `snails new` and `bin/build-image`, and is not committed.

## The results

All figures were measured on 2026-11-10 on one machine: AMD Ryzen 7 260, 8 cores with 16 hardware threads, 16 GB of memory, Docker 29.9.1, k6 2.3.0. The apps ran on threads 4–15; the load generator ran on threads 0–3.

Versions behind the numbers, so a later run can say what changed:

| component | version |
|---|---|
| Rails | 8.1.4.1 |
| Puma | 8.0.2 |
| Ruby in the Rails image | 4.0.9 |
| Snails | v0.46.2 (`e18e17b`) |
| k6 | 2.3.0 |

### Throughput

`results/2026-11-10-no-logging/summary.tsv`, 15 seconds per measurement, three rounds, per-request logging off.

| target | 8 | 32 | 64 | 128 | p95 at 32 | peak memory at 32 |
|---|---:|---:|---:|---:|---:|---:|
| snails | 43,680 | 57,863 | 57,103 | 51,100 | 1.12 ms | 39 MiB |
| rails-cluster | 16,761 | 18,547 | 19,530 | 20,129 | 3.99 ms | 866 MiB |
| rails-default | 4,862 | 4,920 | 4,807 | 4,699 | 9.44 ms | 141 MiB |

The rows are the logging-off variants of the targets named in [What is measured](#what-is-measured). Peak memory is sampled every 50 ms from the container's cgroup counter while the load runs.

`results/2026-11-10-basic/summary.tsv` sweeps the same targets with logging on, and adds the baseline:

| target | 8 | 32 | 64 | 128 | p95 at 32 | peak memory at 32 |
|---|---:|---:|---:|---:|---:|---:|
| baseline | 84,995 | 94,326 | 92,923 | 74,875 | 0.76 ms | — |
| snails | 37,376 | 35,316 | 34,269 | 25,830 | 1.75 ms | — |
| snails-single-worker | 21,141 | 19,892 | 17,607 | 17,310 | 2.04 ms | — |
| rails-cluster | 13,747 | 14,040 | 11,538 | 14,865 | 4.80 ms | — |
| rails-default | 4,024 | 3,956 | 3,362 | 3,843 | 10.81 ms | — |

That run predates peak sampling, so its last column is empty rather than guessed.

How to read it:

- **The baseline sets the ceiling.** It holds around 92,000–94,000 requests per second from 32 to 64 connections and falls at 128. Both apps reach their own limit below it, so neither is limited by the generator.
- **Snails reaches its limit early and stays flat.** With logging on it is already at 37,000 at 8 connections and holds 34,000–35,000 through 64; with logging off the same shape peaks higher, at 57,863. The drop at 128 is queueing, not a lower ceiling: the response time rises while throughput falls.
- **One worker does not scale.** `snails-single-worker` shows the same app capped to one CPU worker: 21,141 against 37,376 at 8 connections. Giving a process more CPUs does nothing if only one worker can run application code.

Logging costs both frameworks. With the per-request line off, Rails gains about 1.4× at every connection level and Snails gains more as concurrency rises. Turned off, Snails answers 57,863 against the baseline's 94,326, about 61% of the ceiling.

### Launch time and idle memory

`results/2026-11-10-boot/boot.tsv`, five rounds, targets interleaved. The timer runs inside the container, so container creation and image preparation are excluded. Idle memory is the container's working set one second after the app starts answering, with no load.

| target | launch to first answer | idle memory |
|---|---:|---:|
| snails | 8 ms | 14.2 MiB |
| rails-default | 1,531 ms | 98.4 MiB |
| rails-cluster | 1,556 ms | 184.4 MiB |

- Launch differs by about 190×. Rails pays roughly the same cost with one worker and with twelve: loading the framework dominates, not the worker count.
- Idle memory scales with Rails workers, twelve costing about twice one. A Snails app is a single process and has no such multiplier.
- Launch is the noisiest figure here: a repeat run of the same images put Rails at 1.28 s instead of 1.53 s. Read the ratio, not the millisecond value.

### Memory after load

`results/2026-11-10-no-logging/memory.tsv`, read once the sweep had finished. This is what each app keeps hold of after traffic, as opposed to the `peak memory` column above, which is the maximum during it.

| target | retained |
|---|---:|
| snails | 31.1 MiB |
| rails-cluster | 874.6 MiB |
| rails-default | 133.4 MiB |

`rails-cluster` keeps 28.2× what Snails keeps after traffic, where idle it was 13×: twelve processes that have each served traffic hold more than twelve that have not.

### Image size

`results/2026-11-10-images/sizes.tsv`, read from the built images.

| image | size |
|---|---:|
| snails:bench | 138 MiB |
| rails-api:bench | 416–424 MiB |

This one is a different kind of measurement: what a deploy ships, not something the load generator produces. Most of the gap comes from Rails needing a Ruby interpreter and its gems in the image, while the Snails image carries only the compiled binary.

The Rails figure is a range because two builds of the same app came out 8 MiB apart. The Snails image came out the same size both times. Treat image size as an order-of-magnitude comparison rather than a precise one.

## Reading a run

`bin/bench` prints a median table when it finishes and writes everything under `results/<name>/`:

- `summary.tsv` — one row per target, concurrency level and round
- `memory.tsv` — one reading per target after the load
- `raw/*.json` — each k6 run's own summary
- `raw/*.log` — k6 output; when a run fails, the reason is here

The runs committed before `memory.tsv` existed hold only `summary.tsv`.

A finished run can be re-read without measuring again:

```sh
bin/report                          # newest run under results/
bin/report results/2026-11-10-basic # a named run
bin/report --json                   # machine-readable
```

Look at where throughput stops rising, not at the highest number. The point where more connections no longer produce more requests per second is the app's limit on that machine, and the response time at that point is the queueing cost. If an app's throughput approaches the baseline's, the generator is the limit and the run cannot compare apps.

## Limitations

- **`GET /up` only.** The route touches no database, model or view, so this compares the request path and nothing below it. It says nothing about query performance, rendering, or job throughput.
- **Absolute figures do not travel.** Simultaneous multithreading, power and thermal limits, and background work on a desktop machine all move them. Compare ratios and the point where throughput stops rising, and re-measure on the target host before making a capacity decision.
- **Run-to-run spread is wide.** Across three rounds on this machine, the lowest and highest measurement of the same target and concurrency differed by 1–31%. A 2–3× difference is readable here; a 10–20% difference is not. Raise `--repeat` when the difference you care about is small.
- **Memory readings are one moment each.** Peak memory is sampled every 50 ms, so a shorter spike can be missed; idle and retained readings are single samples. Enough to compare shapes, not to judge leaks.

## Layout

```
apps/snails/         the Snails app (sqlite, serves /up only)
apps/rails-api/      the Rails app (rails new --api, no ActiveRecord)
baseline/nginx.conf  the baseline server
harness/up.js        the k6 driver
bin/bench            throughput and latency runs
bin/boottime         launch time and idle memory
bin/imagesize        image sizes
bin/report           the median table of a finished run
results/             committed tables and run output
```

Both apps answer `/up` with `{"status":"ok"}`. The Rails app differs from generated defaults in three places, all listed in [apps/rails-api/README.md](apps/rails-api/README.md).
